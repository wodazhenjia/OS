# SimOS —— 模拟操作系统实现（题目六原型）

《操作系统分析与设计实习》题目六的 Java Swing 原型。**当前阶段：可运行的垂直切片**——
文件系统、存储管理、设备管理、进程管理、用户接口五大部分已经接通成一条能跑通的链。

---

## 一、快速开始

### 1. 用 IntelliJ IDEA 打开

1. `File → Open`，选择本目录 `SimOS`（**不要**选它的父目录，否则 Maven 工程结构识别不到）；
2. IDEA 会识别 `pom.xml` 并自动导入 Maven 工程（IDEA 2026.1 自带 Maven，无需额外安装）；
3. `File → Project Structure → Project SDK` 选择 **JDK 21**（本机路径 `C:\Users\LSY\.jdks\ms-21.0.11`）；
4. 运行 `src/main/java/cn/edu/scau/os/app/SimOsApp.java` 的 `main` 方法即可。

> 如果想跑无界面自检：给运行配置加上程序参数 `--selftest 600`。

### 2. 用命令行运行

```bat
cd SimOS
run.bat              :: 编译 + 启动图形界面
run.bat selftest     :: 编译 + 运行无界面自检（22 项检查）
run.bat build        :: 只编译打包
```

或者直接用 JDK 21：

```bat
set JDK=C:\Users\LSY\.jdks\ms-21.0.11
%JDK%\bin\javac -encoding UTF-8 -d target\classes (dir /s /b src\main\java\*.java)
%JDK%\bin\java -Dfile.encoding=UTF-8 -cp target\classes cn.edu.scau.os.app.SimOsApp
```

打包好的可执行 jar：`target\simos.jar`（`java -jar target\simos.jar`）。

## 二、1 字节指令集（全项目共用，已固化）

指导书硬性要求"每条指令在文件中占 1 字节"，编码方案如下（`Opcode.java`）：

| 编码 | 二进制 | 助记符 | 语义 |
|---|---|---|---|
| `0x00`–`0x3F` | `00 xxxxxx` | `x=?` | x ← 操作数（0~63） |
| `0x40` | `01 000000` | `x++` | x ← x+1（上界 255） |
| `0x41` | `01 000001` | `x--` | x ← x−1（下界 0） |
| `0x42` | `01 000010` | `!A?` | 申请 A 设备，**后跟 1 字节**使用时间（0~63） |
| `0x43` | `01 000011` | `!B?` | 申请 B 设备，同上 |
| `0x44` | `01 000100` | `!C?` | 申请 C 设备，同上 |
| `0x45` | `01 000101` | `end` | 可执行文件结束，撤销进程 |
| `0x46`–`0xFF` | 其余 | —— | 保留／非法指令，执行时报错并撤销进程 |

汇编源码示例（写入 `.e` 文件时自动汇编）：

```
x=5
x++
!A3
end
```

汇编器同时输出"机器码清单"，这就是指导书里说的"汇编/编译的模拟过程"。

## 四、必须知道的偏差与设计决策（答辩/报告要用）

### 偏差说明 1：FAT 占用盘块数（指导书自身矛盾）

指导书同时给出两个条件：

1. "第 0、1 块存放文件分配表（FAT），第 2 块存放根目录"；
2. "文件分配表中一项需要 1 字节，而磁盘有 256 块，因而有 256 项"。

**这两个条件不能同时成立**：256 项 × 1 字节 = 256 字节 = **4 个盘块**，而 2 个盘块只有 128 字节。
本项目保留"FAT 覆盖全部 256 块"这一功能性要求，因此：

```
FAT 区    = 盘块 0 ~ 3   （4 × 64 = 256 字节 = 256 项，正好放满）
根目录     = 盘块 4
数据区起点 = 盘块 5
```

若要切换成"FAT 恰好占 0、1 块"的解释，只改 `DiskLayout` 里的三个常量即可
（`FAT_BLOCKS=2; ROOT_BLOCK=2; FIRST_DATA_BLOCK=3;` 并把 FAT 表项数改为 128），
全项目盘位都由这三个常量派生，其它文件无需改动。

### 偏差说明 2：并发用"单线程心跳 + 全局锁"而不是多真线程

指导书提示"可能需要多线程编程才能保证这几种任务的并发"。本项目用**一个时间脉冲**顺序推进：

```
① 随机新进程诞生 ② 闲逛让位检查 ③ 中断检查 ④ 解释执行一条指令 ⑤ 设备倒计时 ⑥ 系统时钟+1、时间片-1
```

整个脉冲持有唯一的模拟锁（`Kernel.lock()`），界面取快照、用户命令也抢这把锁。
这样做的好处是**模拟结果完全可复现**（演示时很重要，固定随机种子），同时完全满足并发语义。
若验收要求"看得见的多线程"，可把设备倒计时/时钟递增拆成独立线程——因为所有状态访问都在同一把锁内，
拆分不影响正确性，只是不再逐位可复现。**这一点建议在报告里主动写明**。

### 偏差说明 3：文件名的硬约束（实现中踩过的坑）

目录项的名字段只有 **3 字节**、扩展名段只有 **1 字节**，所以：

* 文件名/目录名最长 **3 个字符**（只允许字母数字），扩展名最长 **1 个字符**；
* 普通文本文件**不带扩展名**（指导书本身也只用扩展名区分"可执行文件 e"与"目录无扩展名"）；
* 超长名字**直接报错**，不做静默截断——早期版本截断后导致"刚创建的文件立刻找不到"，是本次实现中最隐蔽的 bug 之一。

演示数据因此命名为 `/hi.e`、`/aa/big.e`、`/doc/rme` 这种 3 字符风格。

### 其他已固化的设计决策

* **设备使用时间的单位**：与"指令的一个时间单位"一致，即设备倒计时按同样的脉冲递减。
  指导书说"时间单位自定（例如：秒）"，若要让设备倒计时与指令单位分离，改 `DeviceManager.tick()` 的调用频率即可。
* **设备指令的 PC 语义**：申请成功 → 推进 PC 再阻塞；申请失败 → PC 保持不变，唤醒后重新执行整条申请。
  对应真实系统中"设备分配失败则阻塞等待，成功后该指令完成"。
* **设备等待队列**：申请成功与失败都挂入该设备类型的等待队列，
  这样倒计时归零时才能按队列顺序把使用者唤醒、把等待者唤醒（这是"设备空闲但进程永远醒不来"这个 bug 的根因）。
* **`!X?` 是双字节指令**（第二字节为使用时间），仍满足"指令按字节存储在磁盘块里"。

## 六、自检覆盖范围

`run.bat selftest` 会跑 22 项检查，覆盖：

1. **指令集**：汇编、反汇编、机器码逐字节比对、立即数越界与设备时间越界被拒；
2. **文件系统**：可执行文件数量、目录/文件数量、根目录 8 项上限、
   6 条必做命令的功能与错误路径（重复建目录、非空目录 rmdir、超长文件名）、
   用汇编源码创建 `.e` 文件并反汇编回读；
3. **进程/内存/设备/调度/中断**：创建进程、内存分配、时间片轮转发生、
   设备分配与等待队列、I/O 中断唤醒、进程跑完输出结果。

自检结果（600 个时间单位）：**通过 22 项，失败 0 项**，日志见 `runtime/selftest.log`。

## 七、界面说明

界面严格按指导书"图 1 模拟操作系统的屏幕显示布局和内容"排布，11 个区块：

| 图 1 区块 | 界面位置 |
|---|---|
| 系统时钟 | 第一行左一 |
| CPU / 正在运行进程 ID | 第一行左二 |
| 时间片 | 第一行左三 |
| 用户命令接口 | 第一行左四 + 底部命令输入框 |
| 就绪队列进程 ID | 第二行左一 |
| 阻塞队列进程 ID、等待时间 | 第二行左二 |
| 执行进程中间结果 | 第二行左三 |
| 磁盘目录结构 | 第二行左四（JTree） |
| 正在执行的指令 | 第三行左一 |
| 进程执行完，显示结果 | 第三行左二 |
| 主存用户区使用情况 | 第三行左三（彩色分块，按进程着色） |
| 磁盘使用情况 | 第三行左四（256 格位图：系统区/已分配/空闲/坏块） |
| 设备使用情况、内存分配表、PCB 区、磁盘摘要 | 第四行 |

菜单功能：暂停/继续、单步执行一个时间单位、调整时间单位长度、重新初始化、切换存储管理算法、
调整时间单位长度（滑块）、命令用法、关于/设计说明。

**时间单位长度可运行中实时调整**：底部滑块范围 50~1500 ms（向左更慢、向右更快），
滑块右侧标签实时显示"当前周期（≈多少个时间单位/秒）"，菜单「模拟控制 → 调整时间单位长度…」
提供同一个调节框，两处始终同步。实现上只改 `CPU` 的 volatile 周期字段、脉冲循环每轮重新读取，
**不重启脉冲线程**：早期版本用 `Kernel.setPulseMillis()` → `cpu.stop()` + `cpu.start()` 实现，
而 `stop()` 并不等待旧线程退出、新线程又把 `running` 置回 `true`，于是旧线程睡醒后继续循环，
出现多个脉冲线程同时推进模拟（时间片飞转、日志暴涨）；现在 `stop()` 会 `join()` 等线程真正退出。
